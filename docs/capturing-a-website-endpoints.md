# Capturing a website's observed endpoints into an OpenAPI 3.1 document

This tutorial walks through turning ezcap's local, metadata-only network
observations into an OpenAPI 3.1 document. The workflow uses:

- the **browser extension** to report navigation context,
- the **Native Messaging host** to bridge browser messages to the daemon,
- the **eBPF or libpcap capture backend** to observe network metadata,
- a sandboxed **Lua driver** to reduce and describe those observations,
- the **specgen emitter** to produce the OpenAPI document.

## What this produces, and what it does not

The OpenAPI document generated by this tutorial describes **observed network
destinations** such as:

- transport (`tcp`, `udp`, or another normalized value),
- remote address and port,
- DNS query name when available and permitted by redaction policy,
- capture backend (`ebpf` or `pcap`),
- direction and interface when exposed by the backend,
- attribution confidence annotations.

It does **not** recover full REST route templates such as:

```text
POST /api/v1/checkout
GET  /api/v1/products/{id}
```

ezcap is deliberately metadata-only and does not decrypt TLS, inspect HTTP
bodies, read cookies, or capture packet payloads. For HTTPS traffic, the URL
path and HTTP method live inside the encrypted application data and are not
available to ezcap. The generated OpenAPI is therefore a **catalog of observed
metadata surfaces**, not a substitute for instrumenting an application or
using a service-worker/API-first development workflow.

> **Current integration status:** the Lua driver engine and specgen code are
> present in `ezcap_core`, but the daemon run loop does not yet load drivers or
> provide a file sink for generated specs. The Lua example below matches the
> existing `lezcap` binding surface; to run it end-to-end you need to wire
> `DriverEngine` into the daemon and add the allowlisted export sink described
> in "Exporting the generated document" below.

## End-to-end flow

```text
website request
      │
      ▼
eBPF / libpcap backend          capture layer
      │
      ▼
normalized event
      │
      ▼
redactor + policy engine        metadata-only enforcement
      │
      ▼
Lua driver engine               on_event(event)
      │
      ▼
lezcap.endpoint.declare(...)    descriptor collection
      │
      ▼
lezcap.spec.generate(...)       pure specgen emitter
      │
      ▼
allowlisted daemon/operator sink → observed-endpoints.openapi.json
```

The browser extension does not talk to the driver engine. It reports
navigation evidence to the daemon through the Native Messaging host. That
evidence is used by the correlator to attach confidence to events; the driver
receives the already-redacted result.

## Prerequisites

1. Build and test the C++ project:

   ```sh
   git submodule update --init --recursive
   cmake --preset default
   cmake --build --preset default
   ctest --preset default
   ```

2. Build the browser extension:

   ```sh
   cmake --build --preset default
   ```

   The unpacked Chromium and Firefox builds are under
   `extension/dist/chromium` and `extension/dist/firefox`.

3. Install the Native Messaging host:

   ```sh
   native_host/install/install-linux.sh
   ```

4. Load the extension in your browser. See `native_host/install/README.md`
   for Chromium and Firefox loading instructions and extension-ID matching.

5. Run the daemon with a validated configuration:

   ```sh
   ezcap-daemon --check-config /etc/ezcap/ezcap.conf.json
   sudo ezcap-daemon --config /etc/ezcap/ezcap.conf.json
   ```

   Use `prefer_ebpf: true` when the eBPF backend is available. If it is not,
   ezcap can start in pcap fallback mode; attribution confidence will be
   capped at the probable band (`0.69`) because pcap cannot identify a
   browser process.

## Step 1: Let the extension provide navigation context

In Chromium or Firefox, load the target website in a normal browser tab. The
extension's background service worker:

1. connects to `com.ezcap.host` via Native Messaging,
2. sends `hello` and `subscribe`,
3. reports `http`/`https` navigation updates from `tabs.onUpdated` to the
   daemon for correlation.

The extension intentionally does not read page content. It sends only the
browser-level evidence that is visible through the `tabs` permission; the
daemon applies redaction before any downstream component sees a URL.

To generate more observations, reload the page and exercise the site:

- open a few internal pages,
- trigger search or filter interactions,
- perform any normal actions that create network requests,
- keep the tab in the foreground while capture is running.

The daemon observes connection and DNS metadata only. The extension's role is
to make tab/process attribution possible where evidence exists; it is not a
recorder of HTTP routes.

## Step 2: Create a Lua driver manifest

Place the driver and manifest in an allowlisted driver directory. The bundled
first-party layout is `scripts/lua/`; an installed daemon should use an
absolute, canonical, allowlisted path.

Create `endpoint-catalog.manifest.json`:

```json
{
  "name": "endpoint-catalog",
  "version": "1.0.0",
  "script": "/absolute/path/to/endpoint-catalog.lua",
  "description": "Collects redacted connection metadata and generates an OpenAPI 3.1 document.",
  "capabilities": ["capture", "events", "endpoint", "spec", "log"],
  "event_types": ["connection", "dns"],
  "max_endpoints": 8,
  "max_subscriptions": 4
}
```

Capability choices:

- `capture` enables `lezcap.capture.register_filter`,
- `events` enables `lezcap.event`,
- `endpoint` enables `lezcap.endpoint.declare`,
- `spec` enables `lezcap.spec.generate`,
- `log` enables bounded structured logging.

`event_types` is a reduction over the daemon pipeline. This driver subscribes
to `connection` and `dns`, but the Lua code below focuses on TCP connection
metadata for the OpenAPI catalog.

## Step 3: Write the Lua driver

Create `endpoint-catalog.lua`:

```lua
-- ezcap endpoint-catalog driver
--
-- Receives already-redacted connection metadata, turns each unique
-- destination into a metadata-only endpoint descriptor, and generates an
-- OpenAPI 3.1 document in memory. The sandbox has no io module, so this
-- script never writes the file itself; an allowlisted daemon/operator sink
-- owns that final step.

local MAX_ENDPOINTS = 8
local observed = {}
local order = {}

local function clean_host(value)
  value = tostring(value or "")
  value = string.gsub(value, "[^%w_-]", "_")
  value = string.gsub(value, "^_+", "")
  if #value == 0 then
    return "unknown"
  end
  return string.sub(value, 1, 56)
end

local function descriptor_for(event)
  local net = event.network or {}
  local host = net.dns_query_name or net.remote_address or "unknown"
  local host_text = tostring(host)
  local port = net.remote_port or 0
  local transport = net.transport or "other"
  local name = clean_host(host_text) .. "_" .. tostring(port)
  local summary = "Observed " .. transport .. " destination " ..
      host_text .. ":" .. tostring(port)

  return {
    name = name,
    namespace = "observed",
    version = "1.0",
    kind = "event",
    summary = string.sub(summary, 1, 256),
    description = "Inferred from redacted ezcap network metadata. " ..
        "No HTTP method, URL path, headers, body, or credentials are available.",
    metadata_only = true,
    confidence = "source " .. tostring(event.source or "unknown") ..
        " confidence " .. tostring(event.confidence or 0),
    attribution = {
      "source=" .. tostring(event.source or "unknown"),
      "confidence_is_daemon_assigned"
    },
    privacy = {
      "remote_address and dns_query_name are redacted before driver delivery",
      "no payload, headers, cookies, or credentials are captured"
    },
    response = {
      type = "object",
      properties = {
        transport = { type = "string", enum = { "tcp", "udp", "icmp", "other" } },
        direction = { type = "string", enum = { "inbound", "outbound", "unknown" } },
        remote_address = { type = "string" },
        remote_port = { type = "integer" },
        dns_query_name = { type = "string" },
        interface = { type = "string" },
        backend = { type = "string", enum = { "ebpf", "pcap" } }
      },
      required = { "transport", "remote_address", "remote_port" }
    }
  }
end

local function endpoint_key(event)
  local net = event.network or {}
  local host = net.dns_query_name or net.remote_address or "unknown"
  return tostring(net.transport or "other") .. ":" ..
      tostring(host) .. ":" .. tostring(net.remote_port or 0)
end

function on_load(ctx)
  lezcap.log.info("endpoint-catalog loaded")
  return true
end

function on_start(ctx)
  local ok, err = lezcap.capture.register_filter({
    event_type = "connection",
    transport = "tcp",
  })
  if not ok then
    lezcap.log.error("filter registration failed: " .. tostring(err))
    return false
  end
  return true
end

function on_event(event)
  if event.event_type ~= "connection" then
    return
  end

  local key = endpoint_key(event)
  if observed[key] then
    return
  end
  if #order >= MAX_ENDPOINTS then
    lezcap.log.warn("endpoint limit reached; ignoring additional destinations")
    return
  end

  local descriptor = descriptor_for(event)
  local ok, err = lezcap.endpoint.declare(descriptor)
  if not ok then
    lezcap.log.warn("endpoint declare failed: " .. tostring(err))
    return
  end

  order[#order + 1] = key
  observed[key] = descriptor
end

function on_stop()
  local descriptors = {}
  for _, key in ipairs(order) do
    descriptors[#descriptors + 1] = observed[key]
  end

  if #descriptors == 0 then
    lezcap.log.warn("no observed endpoints to export")
    return true
  end

  local spec, err = lezcap.spec.generate("openapi-3.1", descriptors)
  if not spec then
    lezcap.log.error("spec generation failed: " .. tostring(err))
    return true
  end

  lezcap.log.info("generated OpenAPI bytes=" .. #spec ..
      " endpoints=" .. #descriptors)
  return true
end
```

Important points in the example:

- `lezcap.capture.register_filter` is a **reduction** over the event pipeline;
  it can only narrow which events this driver receives.
- `lezcap.endpoint.declare` validates the descriptor before storing it.
- `metadata_only` must be `true`; a driver that passes `false` receives a
  policy violation, not a silently rewritten descriptor.
- `lezcap.spec.generate` returns the OpenAPI 3.1 document as a string in
  memory. The Lua sandbox intentionally has no `io` module, so the script
  cannot write that string to disk.
- The OpenAPI emitter serializes JSON, not YAML. Name the output file
  accordingly, for example `observed-endpoints.openapi.json`.

## Step 4: Pin the driver with a hash

After writing the Lua file, compute its SHA-256 and add `script_sha256` to the
manifest:

```sh
sha256sum /absolute/path/to/endpoint-catalog.lua
```

Add the lowercase hex value to the manifest:

```json
{
  "name": "endpoint-catalog",
  "version": "1.0.0",
  "script": "/absolute/path/to/endpoint-catalog.lua",
  "script_sha256": "<64-lowercase-hex-characters>",
  "capabilities": ["capture", "events", "endpoint", "spec", "log"],
  "event_types": ["connection", "dns"],
  "max_endpoints": 8,
  "max_subscriptions": 4
}
```

The driver engine verifies the pin before loading the script. Do not copy a
hash from this document; calculate the hash for the file as it exists on your
machine.

## Step 5: Export the generated document

Lua cannot write the OpenAPI file. `src/specgen/` is a pure, side-effect-free
library and returns the generated text to the caller. The daemon or an
operator-side tool must own the final file write.

### Recommended daemon-owned sink

The safest production path is an allowlisted daemon sink that:

- uses an absolute output directory,
- rejects symlinks and path traversal,
- caps output at the existing 512 KiB spec size limit,
- writes only generated spec text,
- runs after driver teardown or after an explicit service-owner command.

For example, after `on_stop`, the daemon can retrieve the descriptors from
`DriverInstance::host_state().endpoints` and call:

```cpp
ezcap::specgen::Format format = ezcap::specgen::Format::OpenApi31;
ezcap::specgen::GenerationContext context{
    "driver:endpoint-catalog",
    ezcap::version_string(),
    1,
};

std::string output;
std::string error;
if (!ezcap::specgen::generate(format, instance->host_state().endpoints,
                              context, output, error)) {
  // structured error; never partially write the file
}

// write `output` through the allowlisted sink
```

Keep this write outside the capture and IPC hot paths, and subject it to the
same metadata-only and storage rules as the rest of the daemon.

### Development-only harness

For a quick local check, a small first-party C++ harness can call
`ezcap::specgen::generate` directly and write the returned string with
`std::ofstream`. This is an operator tool, not part of the Lua sandbox. Use an
absolute output path and validate all inputs as untrusted.

## Step 6: Read the resulting OpenAPI

The emitter produces OpenAPI 3.1 JSON. A representative path from the example
driver looks like:

```json
{
  "openapi": "3.1.0",
  "info": {
    "title": "ezcap generated API",
    "version": "0.1.0",
    "summary": "Generated from ezcap endpoint descriptors",
    "x-ezcap-source": "driver:endpoint-catalog",
    "x-ezcap-generated": "synthetic; contains no observed data"
  },
  "paths": {
    "/observed/example_com_443/v1.0": {
      "post": {
        "operationId": "observed.example_com_443",
        "summary": "Observed tcp destination example.com:443",
        "x-ezcap-kind": "event",
        "x-ezcap-metadata-only": true,
        "x-ezcap-confidence": "source ebpf confidence 0.80",
        "responses": {
          "200": {
            "description": "Success",
            "content": {
              "application/json": {
                "schema": {
                  "$ref": "#/components/schemas/observed_example_com_443_response"
                }
              }
            }
          }
        }
      }
    }
  }
}
```

The exact values depend on the observed destination and active redaction
policy. `x-ezcap-kind` marks this surface as an event-style endpoint. If you
want channel-oriented output instead, call:

```lua
local spec, err = lezcap.spec.generate("asyncapi-2", descriptors)
```

OpenAPI output is valid JSON, so tools such as Redocly, Spectral, and common
OpenAPI editors can consume `observed-endpoints.openapi.json` directly.

## Privacy checklist

Before using a generated file beyond local analysis:

- Confirm the driver manifest requests only needed capabilities.
- Keep `metadata_only` set to `true` in every descriptor.
- Do not add example values copied from live observations; generated specs
  already use marked synthetic placeholders.
- Do not add fields such as `payload`, `body`, `cookies`, `authorization`,
  `password`, or `api_key` to driver-emitted descriptors.
- Do not attempt to disable redaction from a driver; the daemon enforces
  metadata-only and redaction before events reach Lua.
- Store exported files in a bounded, allowlisted directory and review them as
  machine-generated artifacts.

## Limitations to report honestly

- HTTPS path and method are not recoverable by ezcap.
- `libpcap` attribution is capped at probable confidence and cannot identify
  tabs on its own.
- eBPF requires the documented kernel/toolchain support; when unavailable, the
  daemon should report a degraded pcap fallback rather than imply eBPF
  accuracy.
- The Lua sandbox has no file, process, raw-socket, or FFI surface. This is a
  privacy guarantee and means file export must live outside the script.
- The driver engine is not yet wired into the daemon's `run()` path. The
  binding example is compatible with the current `lezcap` API, but live
  loading and file export require the integration described above.
